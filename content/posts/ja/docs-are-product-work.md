私はますます、ドキュメントを「最後に足しておくもの」として扱うのが嫌になっています。

オープンソースのプロジェクトにとって、README、環境変数の説明、デプロイ手順、アーキテクチャの説明、境界の宣言は、付属品ではないことが多いです。むしろプロダクトそのものの一部です。

## コードが動くことは、プロジェクトが成立していることを意味しない

多くの作者は「コードが本物なら、人は自然に理解してくれる」と思いがちです。

でも現実はそうではありません。誰かがリポジトリを開いたとき、最初に見るのはコード内部のロジックではなく表紙です。そこで相手はまず、「これは何か」「なぜ存在するのか」「どうやって始めればいいかすぐ分かるか」「デプロイするならどんな外部リソースが必要か」「実際にはどんな場面向けか」を判断します。

これらの問いに答えがなければ、コードがよく書けていても、実際に使われるプロジェクトになるのは難しいです。

## README は静かにプロジェクトの境界を定義している

良い README はインストール方法を説明するだけではありません。プロジェクトの境界も定義しています。

たとえば `smail` のようなプロジェクトでは、機能一覧だけでは足りません。実行時依存、Cloudflare のバインディング、セッション設定、データベースマイグレーション、適用場面、制限まで説明する必要があります。`hostc` でも同じです。クイックスタート、アーキテクチャ、ロードマップは、そのプロジェクトの成熟度や用途を人がどう理解するかに直接影響します。

プロジェクトによっては、トップページが魅力的であることより、安心して先へ進めることのほうが大切です。

## ドキュメントは本当に考え切れているかを暴く

私はかなり残酷だけれど真実だと思うことがあります。ドキュメントでうまく説明できない部分は、プロダクト自体もまだ十分に考え切れていないことが多いということです。

ある概念が作者の頭の中で補完されてはじめて成立するのなら、その抽象化はまだ終わっていません。

だから README を書くことは、私にとって外向きの説明であるだけでなく、内向きの点検でもあります。どの名前がまだ不安定か、どの経路が回りくどいか、どの機能が作者視点でしか「当然」に見えていないかが見えてきます。

## オープンソースはコードを投げることではない

私は「とりあえず公開してから考えればいい」というスタイルにはあまり賛成しません。早く公開してはいけないという意味ではありませんが、本当に使えるプロジェクトにしたいなら、入口は少なくとも受け入れられる水準まで整えるべきです。

他人はあなたの不足した前提を補うためにいるわけでも、環境変数を推測するためにいるわけでもありません。

役に立つオープンソースは、少なくとも避けられたはずの落とし穴を、少しでも減らすべきです。

## だから私はドキュメントをコア作業として扱うようになった

それでリポジトリが派手に見えるわけではないし、すぐに star が増えるとも限りません。でも、プロジェクトの実際の使いやすさはかなり大きく上がります。

もしプロジェクトが理解され、再利用され、デプロイされることを目指すなら、README は締めの作業ではありません。プロダクト作業の一部です。
